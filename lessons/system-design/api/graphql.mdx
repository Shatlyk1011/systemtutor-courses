A profile screen needs a user’s name and a list of recent posts with comment counts. If the existing HTTP API exposes separate user, post, and comment resources, the screen might fetch fields it never displays and make extra requests to fill in the missing ones. **GraphQL** lets a client select related fields from a typed schema in one operation.

![The example REST client requests users, posts, and comments separately. The GraphQL client selects related fields through one endpoint.](https://pub-d143c03df8bc45d5a4589bc793aa52e4.r2.dev/courses/15aa5af8-3541-4385-b8bf-900901675665/gallery/b54ea777-c9d5-413a-90c4-1e4d700d4731)

## Read the schema as a contract

The **Schema Definition Language (SDL)** describes the fields clients may request, their arguments, and their return types. In this excerpt, start at `Query.user`, then follow its return type to see which profile fields are available.

```graphql
type Query {
  user(id: ID!): User
}

type User {
  id: ID!
  name: String!
  posts(limit: Int = 10): [Post!]!
}

type Post {
  id: ID!
  title: String!
  commentsCount: Int!
}
```

Here `user(id: ID!): User` requires an ID but allows the lookup to return `null`. A successful `posts` field returns a list whose items are non-null posts. An empty list `[]` is valid. If a resolver returns null for a field declared non-null, the error propagates to the nearest nullable parent.

## Select fields for the screen

Keep the operation stable and supply changing values through **variables**. Read the operation, then the values and the matching result.

<Tabs items={["Query", "Variables", "Result"]}>
  <Tab value="Query">
    ```graphql
    query GetProfile($id: ID!, $limit: Int!) {
      user(id: $id) {
        name
        posts(limit: $limit) {
          title
          commentsCount
        }
      }
    }
    ```
  </Tab>
  <Tab value="Variables">
    ```json
    { "id": "42", "limit": 3 }
    ```
  </Tab>
  <Tab value="Result">
    ```json
    {
      "data": {
        "user": {
          "name": "Alice",
          "posts": [
            { "title": "Scaling a service", "commentsCount": 14 },
            { "title": "GraphQL resolvers", "commentsCount": 8 },
            { "title": "Choosing a cache", "commentsCount": 2 }
          ]
        }
      }
    }
    ```
  </Tab>
</Tabs>

The client supplied an ID to locate the user. It selected only the name, post titles, and counts for display, so the ID itself is absent from the response. A different screen could request the ID using the same schema.

## Count the reads behind a query

A **resolver** produces the value of a field. Some fields are already present on a parent object. Others require a database or service call. The client’s single operation can therefore trigger several separate reads. [GraphQL field execution](https://graphql.org/learn/execution/)

Suppose the server looks up the user once, loads the list of three posts once, and counts comments separately for each post. That costs **five reads**. Within the posts portion, the one list read followed by one read per post is called the **N+1 problem**. If the data source can return counts for all three post IDs together, the same response costs **three reads** in this example. The improvement comes from how the server loads the data.

![One GraphQL query takes five reads with separate comment-count lookups. Grouping the three counts into one lookup reduces the total to three reads.](/course-images/system-design/api/graphql/graphql-resolver-batching.png)

A server can also bound a list’s length or limit query cost to keep one operation from requesting too much work. A single endpoint that receives many operations and variables needs cache keys that distinguish their results.

## Read, change, or follow data over time

| Operation | What it expresses |
|---|---|
| **Query** | Read selected fields. Independent fields may resolve concurrently. |
| **Mutation** | Change state and select fields from the result. Top-level mutation fields in one operation execute serially. |
| **Subscription** | Receive a stream of results as events occur. |

For example, a schema could define `createPost(input: CreatePostInput!): Post!` on its `Mutation` type. The caller supplies a title and content and can select `id` and `title` from the created post in the same operation.

Many servers accept a JSON request at `POST /graphql`. Some also accept read-only queries over GET. When a valid operation executes, the HTTP response can be successful even if a field failed. Inspect both `data` and `errors` to see what the screen can use. A failure before execution, such as an invalid HTTP request, can also produce an HTTP error. [GraphQL over HTTP](https://graphql.org/learn/serving-over-http/)

## Key Takeaways

- **A schema** defines the fields, arguments, relationships, and nullability a client can depend on.
- **A selection** determines which fields the response contains. Variables supply values without rewriting the operation.
- **Resolvers** determine the data-access work behind the selection. Count backend reads as well as client requests.
