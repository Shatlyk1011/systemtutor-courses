<Callout title="Lesson goal" type="info">
  Specify the inputs, successful result, and error behavior a client needs, then recognize three ways to express that contract.
</Callout>

**Before you begin** — [HTTP](/courses/system-design/docs/networking/http).

A weather app needs to display the temperature for a city. The team building the screen should be able to tell what to send, what units it will receive, and what to show for an unknown city. Those decisions form part of an **application programming interface (API)**, the contract one software component exposes to another.

## Follow a request against a contract

Suppose the weather service accepts a city identifier and returns a temperature in degrees Celsius. It also defines a response for an unknown city. The app can format a successful reading or display the documented error. The service can change how it stores observations as long as it keeps those promises.

![A weather app sends a request through the API contract and receives a response from the weather service.](https://pub-d143c03df8bc45d5a4589bc793aa52e4.r2.dev/courses/15aa5af8-3541-4385-b8bf-900901675665/gallery/f02074f4-2699-47b5-9285-6fd01310908d)

Think through the contract in order. **Input** tells the caller how to identify the city. **Output** specifies the field, its type, and its units. **Error behavior** tells the caller how to distinguish an unknown city from a successful reading of zero degrees. A numeric field alone would leave the caller guessing.

## Identify the boundary

A local function such as `Math.max` and an HTTP endpoint both have interfaces. A local library call can run inside the calling program. A request to a remote service crosses a network boundary and can time out while the service is still working.

![A local API runs on the caller’s machine. A network API sends the request to a remote service.](https://pub-d143c03df8bc45d5a4589bc793aa52e4.r2.dev/courses/15aa5af8-3541-4385-b8bf-900901675665/gallery/85215ab3-0ce2-44ed-978e-2985e5c1a1a7)

Knowing the boundary helps a designer choose what failures the contract must describe. A valid city identifier is enough to construct a weather request. Receiving a timely reply also depends on the network and the remote service.

## Express the same read three ways

Suppose a client needs user 42’s name. Each of the next lessons expresses that operation with a different contract.

| Style | What the client specifies | Where to see it |
|---|---|---|
| REST | A resource URI and an HTTP method, such as `GET /users/42`. | [REST](/courses/system-design/docs/api/rest) |
| GraphQL | Fields from a typed schema, such as the name belonging to user 42. | [GraphQL](/courses/system-design/docs/api/graphql) |
| RPC | A named operation and arguments, such as `GetUser(42)`. | [RPC](/courses/system-design/docs/api/rpc) |

A service can also publish events or stream updates when clients need to hear about changes as they happen. The right contract follows from what the caller needs to do.

## Check your understanding

The weather service changes its storage engine this week. Next week it keeps the same response field but starts reporting Fahrenheit. Which change affects the app?

<details>
<summary>Compare your reasoning</summary>

The app can keep using the same contract after the storage change. Switching units changes the meaning of a successful response. The app would display the wrong temperature even though it could still parse the number.

</details>

## Key Takeaways

- **A contract** defines the meaning of inputs, results, and errors for callers.
- **The boundary** determines which failures can occur between issuing a call and receiving its result.
- **REST, GraphQL, and RPC** organize client interactions around resources, selected fields, and named operations.
