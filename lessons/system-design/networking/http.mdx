**HTTP (Hypertext Transfer Protocol)** defines how clients and servers exchange requests and responses. A request uses a method such as `GET` or `POST` to describe the requested action. The response uses a status code such as `200 OK` or `201 Created` to describe the outcome. These meanings are defined in [RFC 9110, HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html).

<Callout title="Lesson goal" type="info">
  Inspect a request and its response, explain what HTTPS protects, and decide when repeating a request is safe.
</Callout>

**Before you begin** — [DNS](/courses/system-design/docs/networking/dns).

After resolving a hostname and opening a connection, a browser can use HTTP to ask for a page or submit data. HTTP/1.1 and HTTP/2 commonly use TCP. HTTP/3 uses QUIC over UDP.

## Read a request and response together

Suppose an app wants to create a user. It sends `POST /users` to the API, sets `Content-Type: application/json`, and includes the user details in the body. The server creates the record and replies with `201 Created`. Its response can include a `Location` header identifying the new resource and a body containing the representation.

![A request carries a method, path, headers, and optional body. The response carries a status, headers, and optional body.](https://pub-d143c03df8bc45d5a4589bc793aa52e4.r2.dev/courses/85f8547f-b01d-4b2b-be42-1c9f70864b3e/gallery/6949b2f7-7cd3-49b9-b3c4-286c5584f22b)

In this exchange the app is the **client** because it initiated the request. If the API calls another service to finish the work, the API is a client in that second exchange.

    ```js
    const response = await fetch("https://api.example.com/users", {
      method: "POST",
    ```

    ```python
    import json
    from urllib.request import Request, urlopen

    request = Request(
        "https://api.example.com/users",
        method="POST",
        headers={"Content-Type": "application/json"},
        data=json.dumps({"username": "alice"}).encode(),
    )
    with urlopen(request) as response:
        print(response.status, response.headers.get("Location"))
    ```

## Interpret the method and status together

| Method | What the client requests | Example |
|---|---|---|
| `GET` | Retrieve a representation. | Read `/users/42`. |
| `POST` | Ask the target to process the submitted data. | Create a user through `/users`. |
| `PUT` | Create or replace the state at a particular URI, if allowed by the API. | Store the complete profile at `/users/42`. |
| `PATCH` | Apply the supplied changes to the target. | Set one field on the profile. |
| `DELETE` | Remove the association between the target URI and its current functionality. | Remove access to `/users/42`. |

An HTTP **status code** describes the outcome of this exchange. `1xx` reports interim progress, `2xx` success, `3xx` redirection or cache-related outcomes, `4xx` a problem fulfilling this request, and `5xx` a server-side failure. Read the specific code. A `404` says the target was not found or its existence was withheld. A `503` says the service is temporarily unavailable. Neither tells you exactly what happened inside a database. [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html)

## Reason about a lost response

The server may finish a request even when the client never receives the reply. A method is **idempotent** when repeating an identical request has the same *intended effect* as sending it once. `GET`, `PUT`, and `DELETE` have this property. Two identical `DELETE` calls can receive different responses, such as a successful deletion followed by `404`, while leaving the resource in the same final state.

A `POST /users` that creates a user on every call could create two users after a retry. For `PATCH`, inspect the operation. Setting a field to a fixed value can be idempotent. Incrementing it by one changes the result each time. The API contract must tell the client how to handle an uncertain outcome.

## Protect an exchange with HTTPS

HTTPS uses **Transport Layer Security (TLS)** to authenticate the server and protect HTTP data in transit from disclosure or alteration. During a typical first connection, the client checks the server’s certificate and the peers establish keys for protected traffic. The receiving service can then read the request and apply its own access rules.

## Key Takeaways

- **Requests** identify a target and operation. Responses describe the outcome through a status, headers, and optional content.
- **Idempotence** concerns the intended effect of repeating a request. The observed replies can differ.
- **HTTPS** protects HTTP traffic between TLS endpoints. The service still decides who may perform the requested action.
