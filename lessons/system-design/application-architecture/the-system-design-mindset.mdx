**Before you begin** — [Observability and Operations](/courses/system-design/docs/application-architecture/observability-and-operations).

A user uploads a profile photo. The team wants uploads to be “fast and reliable.” To turn that request into a design, first trace what happens to the photo. Then decide what success looks like from the user's point of view.

## Follow the photo

The application **moves** the uploaded bytes to a worker, which **transforms** the image into the size the profile page needs. The system **stores** the finished image in object storage and its location in the database. When the profile page loads, it can use that location to fetch the image.

![An uploaded photo goes through a worker. The transformed image goes to object storage and its URL goes to the database.](https://pub-d143c03df8bc45d5a4589bc793aa52e4.r2.dev/courses/de9ef765-c009-496e-b966-629ad6184037/gallery/22a251e0-cf18-48d2-8d81-f730a7b4e250)

Two different operations are visible to the user. Uploading a photo creates new data. Opening a profile retrieves an existing photo. An outage in the transformation worker can delay new photos while already stored photos remain available. Set requirements for each user operation separately.

## Choose an availability measure

**Availability** measures how often the service is usable under a definition you choose. For a time-based measure, divide usable time by total time in the measurement window. For a request-based measure, divide successful eligible requests by all eligible requests. A failed minute counts equally at every traffic level in the first measure. In the second, the effect depends on how many requests failed.

For a time-based target over a 365-day year, the allowed downtime is the fraction of the year outside the target. At 99.9% availability, that is 0.001 × 365 × 24 hours, or **8.76 hours**.

| Availability target | Allowed downtime in 365 days |
| --- | --- |
| 99% (two nines) | 3.65 days |
| 99.9% (three nines) | 8.76 hours |
| 99.99% (four nines) | 52.56 minutes |
| 99.999% (five nines) | About 5.26 minutes |

Real services can report separate histories for different operations. In this example, Git operations and API requests have their own 90-day histories. A single percentage for the whole product would hide those differences. [GitHub Status](https://www.githubstatus.com/)

![GitHub’s status page shows separate 90-day uptime histories for Git operations, webhooks, API requests, issues, pull requests, and Actions.](https://pub-d143c03df8bc45d5a4589bc793aa52e4.r2.dev/courses/de9ef765-c009-496e-b966-629ad6184037/gallery/32555285-c0fa-4161-9005-9552c508bf4b-Screenshot-2026-08-19-at-16.09.11.png)

A **service level objective (SLO)** specifies a target and window, such as serving 99.9% of eligible profile reads successfully over 30 days. A **service level agreement (SLA)** records a commitment to customers, including any agreed consequences for missing it. An engineering team can measure its own SLO without making a contractual commitment. [Google SRE on service level objectives](https://sre.google/sre-book/service-level-objectives/)

## Separate correctness, capacity, and speed

**Reliability** concerns whether the system keeps doing the right thing. Returning another user's photo quickly would still be a failure. **Fault tolerance** is the ability to continue providing a specified service after a fault. An additional worker provides **redundancy**. For that redundancy to help, work must reach the surviving worker and it must have enough capacity.

**Throughput** counts completed work per unit of time, such as photos per second. **Latency** measures elapsed time for one operation, such as the time from upload until the resized photo is ready. Decide where each timer starts and stops before comparing measurements.

![Fault tolerance keeps a service operating through failures. Redundancy provides spare capacity. ## Check your understanding

Suppose one worker resizes a photo in 200 ms, processes one photo at a time, and always has another photo waiting. A second identical worker can resize another photo independently. What happens to throughput and latency?

<details>
<summary>Compare your reasoning</summary>

One worker finishes about five photos per second. Together the two can finish about ten per second under these assumptions. Each resize still takes 200 ms. A user can see a faster result if their photo spends less time waiting for a worker. Measure the wait and the resize separately to see which changed.

</details>

## Key Takeaways

- Trace where data **moves, changes, and persists** so each requirement names a user-visible operation.
- Define availability using a success criterion, a denominator, and a window. An **SLO** sets a target and an **SLA** records a customer commitment.
- **Throughput** measures completed work per interval. **Latency** measures time for one operation, including any waiting inside the chosen boundary.
