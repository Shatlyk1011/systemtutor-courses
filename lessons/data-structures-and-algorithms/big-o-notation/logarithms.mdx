## Logarithms and Complexity Growth

A logarithm is the mathematical inverse of exponentiation.

If:

$$
b^x = n
$$

then:

$$
\log_b(n) = x
$$

In plain English, a logarithm asks: **what power do we need to raise $b$ to in order to get $n$?**

```text
Exponent:   2⁴ = 16       (2 multiplied by itself 4 times equals 16)
Logarithm:  log₂(16) = 4  (How many times do we multiply 2 to get 16? Answer: 4)
```

Halving a problem naturally gives a base-2 logarithm. If a search kept one third of the candidates each time, base 3 would describe the number of reductions. Changing between fixed bases greater than 1 multiplies the result by a constant, so either process has logarithmic growth.

| Value ($n$) | Base 2 Logarithm ($\log_2 n$) | Exponent Equivalent ($2^x = n$) |
| :--- | :--- | :--- |
| $1$ | $0$ | $2^0 = 1$ |
| $2$ | $1$ | $2^1 = 2$ |
| $4$ | $2$ | $2^2 = 4$ |
| $8$ | $3$ | $2^3 = 8$ |
| $16$ | $4$ | $2^4 = 16$ |
| $32$ | $5$ | $2^5 = 32$ |
| $64$ | $6$ | $2^6 = 64$ |
| $1{,}024$ | $10$ | $2^{10} = 1{,}024$ |
| $1{,}048{,}576$ (~1M) | $20$ | $2^{20} = 1{,}048{,}576$ |
| $1{,}073{,}741{,}824$ (~1B) | $30$ | $2^{30} = 1{,}073{,}741{,}824$ |

<Callout title="The Halving Intuition" type="info">
A great way to think about $\log_2(n)$ in programming is: **how many times can you cut $n$ in half until you reach 1?**

For example, starting with $n = 16$:
$$16 \xrightarrow{\div 2} 8 \xrightarrow{\div 2} 4 \xrightarrow{\div 2} 2 \xrightarrow{\div 2} 1$$
It takes **4 cuts** to bring $16$ down to $1$, so $\log_2(16) = 4$.
</Callout>

## $O(\log n)$ Growth

For a process that repeatedly halves its input, doubling the starting size adds one halving. This is the pattern behind logarithmic growth.

### Example: Binary Search

In a sorted list, Binary Search looks right at the middle item. If the number we want is smaller than the middle item, we throw away the whole right half. If it's bigger, we throw away the left half. We repeat this until we find the item or run out of numbers.

For the target `8` in `[1, 2, 3, 4, 5, 6, 7, 8]`, round the midpoint down. The successive midpoint values are `4 → 6 → 7 → 8`. Three halvings reduce eight candidates to one. You still need a fourth inspection to test that final candidate.

With this inclusive interval and a lower midpoint, the worst case for a nonempty array takes $\lfloor\log_2 n\rfloor + 1$ midpoint inspections. The chart counts one inspected array item per step. From 8 through 15 items, binary search needs at most four inspections. At 16 items, its maximum increases to five.

![Worst-case linear search inspects n items. For 1 through 16 items, binary search increases to 2, 3, 4, and 5 inspections at lengths 2, 4, 8, and 16 respectively.](https://pub-d143c03df8bc45d5a4589bc793aa52e4.r2.dev/courses/ba5422b9-c8ef-4672-b067-9c87b70f4f60/gallery/26dceb12-83b3-4cc0-b579-278d908c99ef)

| Items in List ($n$) | Linear Search $O(n)$ Max Steps | Binary Search $O(\log n)$ Max Steps |
| :--- | :--- | :--- |
| $8$ | $8$ | $4$ |
| $64$ | $64$ | $7$ |
| $1{,}024$ | $1{,}024$ | $11$ |
| $1{,}000{,}000$ (1 Million) | $1{,}000{,}000$ | $20$ |
| $1{,}000{,}000{,}000$ (1 Billion) | $1{,}000{,}000{,}000$ | $30$ |

If you double a list from $1$ million to $2$ million items, a worst-case linear search checks an extra $1{,}000{,}000$ items. The worst-case binary search needs one extra midpoint inspection.

## $O(n \log n)$ Growth

An $O(n \log n)$ algorithm (sometimes called **linearithmic**) combines two parts:

- $n$: doing work on all $n$ items (like looking through or merging items at each step).
- $\log n$: repeating that work across $\log n$ split levels or stages.

| Eight items, sorted in runs of | Merges on this level | Items processed across the level |
| --- | --- | --- |
| 1 item | 4 merges of two singletons | 8 |
| 2 items | 2 merges of two pairs | 8 |
| 4 items | 1 merge of two runs of four | 8 |

Merge sort is one example of this growth rate.

### Example: Merge Sort

Merge Sort splits a list in half over and over until each piece has only 1 item (which takes $\log n$ levels of splitting). It then merges those pieces back together in sorted order.

For eight items, the runs after each merge level have lengths 2, 4, and 8. Each level processes all eight items across its merges. Doubling to sixteen items adds one level and doubles the number of items at each level.

### Comparing $O(\log n)$ and $O(n \log n)$

| Complexity | Growth Speed | Typical Use Case |
|---|---|---|
| $O(\log n)$ | One additional halving per doubling | Searching (like Binary Search) |
| $O(n \log n)$ | A linear amount of work at each of logarithmically many levels | Fast Sorting (like Merge Sort) |

## Logarithms in Recursion

A recursion tree has logarithmic depth when each child is at most a fixed fraction of its parent. Subtracting one at each call instead creates a linear-depth chain.

For a power-of-two input, the following tree has $\log_2 n$ edges along each path from the root to a leaf. Level zero contains the root:

```text
Level 0:                 [Size n]                     --> 1 call
                          /    \
Level 1:           [Size n/2]  [Size n/2]             --> 2 calls
                    /    \        /    \
Level 2:       [n/4]    [n/4]  [n/4]    [n/4]         --> 4 calls
                ...      ...    ...      ...
Level log₂(n): [ 1 ]    [ 1 ]  [ 1 ]    [ 1 ]         --> n calls
```

The total time depends on how many branches the function explores and how much work it does at each level:

1. **Checking only one half $\to O(\log n)$ Time:**
   If the code only follows one branch down (like recursive binary search), the total work is simply the height of the tree:
   $$\text{Total Work} = O(1) \text{ per level} \times \log_2 n \text{ levels} = O(\log n)$$

2. **Working on both halves $\to O(n \log n)$ Time:**
   If the code visits both branches and does $O(n)$ work merging them (like merge sort), every level adds up to $n$ work:
   $$\text{Total Work} = n \text{ work per level} \times \log_2 n \text{ levels} = O(n \log n)$$

## Key Takeaways

- A base-2 logarithm counts the exact number of halvings from a power of two to one.
- Binary search follows one remaining interval and uses one midpoint inspection per iteration. The last candidate still needs checking.
- Merge sort processes all items at each of its logarithmically many merge levels, giving `O(n log n)` time.
- Tree depth describes one path. To estimate total work, also count the work across every branch at each level.
